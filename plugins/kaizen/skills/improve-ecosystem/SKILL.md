# improve-ecosystem

直前までの会話セッションを振り返り、詰まり・不満の原因を特定したうえで、`claude-code-marketplace` の既存プラグインを修正するか新規プラグインを作成するかを判断し、ユーザーの承認を得てから実装する。

## 手順

1. **対象範囲の確認**
   - 特に指示が無ければ、今のスキル実行時点でClaude自身が保持している会話コンテキスト(直前までのやり取り全体)を対象とする。追加のログファイル読み込みは行わない。
   - ユーザーが「もっと前の話」など今の会話コンテキストに含まれない範囲を指しているようであれば、対象を明確化するよう質問する。
   - 会話が長くcompactされていて詰まった箇所の詳細が失われていそうな場合のみ、`~/.claude/projects/<cwdに対応するディレクトリ>/<sessionId>.jsonl` から直近のtranscriptを読み込んでよいかユーザーに確認する(必須ではない)。

2. **原因の特定**
   - 会話を振り返り、詰まり・不満の該当箇所を具体的に指し示す(どの発言・どの作業でつまずいたか)。
   - 原因を以下のいずれかに分類する(複数該当してもよい)。
     - a. 情報不足・毎回同じ前提を説明させられた
     - b. 同じ手順・確認を毎回繰り返させられた
     - c. 危険な操作(rm, force push等)を止めてほしかった/逆に過剰にブロックされた
     - d. 出力形式・粒度がユーザーの期待と食い違った
     - e. 非効率な手順(手動で何度もコマンドを打つ等)だった
   - 原因が特定できない、または単発の一時的な問題(このリポジトリの恒久的な設定に起因しない)と判断した場合は、無理に変更を提案せず「今回はエコシステム側の修正は不要と考えられる」旨をユーザーに伝えて終了する。

3. **修正対象の判断: 既存プラグイン修正 or 新規プラグイン作成**
   - `README.md` の「プラグイン一覧」表と、各プラグインの `plugins/*/.claude-plugin/plugin.json` の `description` を確認する。
   - 特定した原因が既存プラグインの関心領域(例: Git操作なら`git`、CI/CD自動化なら該当バックエンドのプラグイン、メディア変換なら`tools`等)に明確に一致する場合は、そのプラグインに1スキルまたは1hookを追加/修正する。
   - どの既存プラグインにも当てはまらない、独立した新しい関心事だと判断した場合は、新規プラグインの作成を提案する。
   - 原因がhook向き(自動的にガード/整形/検知したい)かskill向き(手順を型化して呼び出したい)かを判断する。
     - 繰り返しの手順・調べ物・生成作業 → skill
     - 危険操作のブロック、ファイル保存後の自動整形など「〜のたびに自動で」 → hook
   - **重要**: このプラグイン自身(`kaizen`)にStop hookなど自動判定のhookを追加することは行わない。本スキルは常に手動起動のみとする制約は変更しない。

4. **変更内容の提案(実装前に必ずユーザーに提示)**
   - 「原因」「対象プラグイン(既存 or 新規)」「追加/修正するファイル一覧」「変更の要約」をユーザーに提示し、実装してよいか確認を求める。
   - この時点でユーザーが変更不要と判断した場合はここで終了する。

5. **実装**
   - 承認を得てから、対象に応じて以下を更新する。
     - 新規プラグインの場合:
       - `plugins/<plugin-name>/.claude-plugin/plugin.json` を作成する(`name`, `description`, `version: "0.1.0"`, skillがあれば`"skills": "./skills/"`, hookがあれば`"hooks": "./hooks/hooks.json"`)。
       - `.claude-plugin/marketplace.json` の `plugins` 配列末尾に `{ "name": "<plugin-name>", "source": "./plugins/<plugin-name>/" }` を追記する。
       - `README.md` の「インストール方法」コードブロックに `/plugin install <plugin-name>@ai-common` を追記し、「プラグイン一覧」表に1行追加する。
     - 既存プラグイン修正の場合:
       - 対象の `plugins/<plugin-name>/skills/<skill-name>/SKILL.md` を新規作成、または既存hookの`hook.sh`/`hooks.json`を修正する。
       - 既存プラグインの `.claude-plugin/plugin.json` の`description`を、追加したスキル/hookの内容に合わせて更新する。
       - `README.md` の「プラグイン一覧」表の該当行の説明文を更新する。
     - スキル/hookの内容は、`plugins/tools/skills/write-diary/SKILL.md` の構成(frontmatter + 概要 + 手順 + 注意事項)に厳密に従う。スキル名にプラグイン名の接頭辞は付けない。組織固有情報(社内ドメイン・レビュワー名等)は含めない。

6. **整合性チェック**
   - 追記した各JSON(`marketplace.json`, `plugin.json`, `hooks.json`)が構文的に妥当か確認する。
   - スキル名がプラグイン内で重複していないか確認する。
   - `README.md`の「インストール方法」と「プラグイン一覧」の両方に反映されているか確認する(既存の全プラグインがこの2箇所に登場しているという既存パターンを崩さない)。

7. **完了報告**
   - 変更したファイルの一覧と差分の要約をユーザーに提示し、最終確認を求める。

## 注意事項

- **手動起動のみ**。Stop hookなどによる自動判定・自動起動の仕組みをこのプラグインやスキル自体に追加しない。
- ユーザーの明示的な承認を得るまで、実際のファイル変更(新規作成・上書き)を行わない。
- 1回の実行で扱う変更は、特定した原因に対応する範囲(基本は1スキルまたは1hook)に絞る。既存スキルの大幅な書き換えや複数プラグインにまたがる大きな変更は、必ず事前にユーザーに相談してから進める。
- 組織固有の情報(社内ドメイン名・レビュワー一覧など)を含めない(README「設計方針」に準拠)。
- 会話の中に含まれる可能性のある機微な情報(トークン、個人情報等)を、生成するSKILL.md等にそのまま転記しない。
- 該当する改善点が見当たらない場合、無理に変更を作り出さない。
