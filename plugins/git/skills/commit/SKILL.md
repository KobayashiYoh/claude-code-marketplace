# commit

現在の変更内容を確認し、関連するファイルのみをステージしてコミットする。

## 手順

1. `git status` で untracked / modified / staged ファイルを確認する。
2. `git diff` (unstaged分) と `git diff --staged` (staged分) の両方を確認し、変更内容を正確に把握する。
   - 差分が無い場合はその旨を伝えて終了する。
3. 今回のタスクと無関係なファイルが含まれていないか確認する。無関係な変更が混ざっている場合はユーザーに確認する。
4. コミットメッセージを作成する。
   - 「何を変えたか」ではなく「なぜ変えたか」を重視する。
   - 1〜2文程度の簡潔な日本語(または対象リポジトリの慣習に合わせた言語)で書く。
   - 対象リポジトリに既存のコミットメッセージの書き方(例: prefix、絵文字の有無)があれば `git log --oneline -20` で確認し、それに合わせる。
   - メッセージの根拠は `git diff` (unstaged分)と `git diff --staged` (staged分)に実際に現れた差分のみとする。system-reminderや会話コンテキストから把握した「diffに出ていない変更」をメッセージに混ぜない。
5. 今回のタスクに関連するファイルのみを `git add <file> <file> ...` のように個別に指定してステージする。
   - `git add -A` や `git add .` のような無差別なステージングは行わない(意図しないファイルの混入を防ぐため)。実際に禁止したい場合はスキル側の自然言語ではなく、プロジェクトの `.claude/settings.json` の `permissions.deny` で `Bash(git add -A:*)` 等を明示的に拒否すること。
6. `.env` や認証情報など秘匿情報を含みそうなファイルが含まれていないか、ステージ後にもう一度 `git status` で確認する。怪しいファイルがあれば内容を確認してからコミットする。
7. HEREDOCでコミットメッセージを渡し、コミットを実行する。
8. コミット後、`git status` で成功を確認する。

## 注意事項

- ユーザーから明示的に「コミットして」という指示が無い限り、勝手にコミットを実行しない。
- push は行わない(pushが必要な場合は別途MCPのgitサーバーやユーザーの指示に従う)。
- pre-commit hook が失敗した場合は `--no-verify` で回避せず、原因を確認して修正する。
